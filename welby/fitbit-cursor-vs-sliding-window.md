# Fitbit Sliding Window vs Cursor-Based Sync

> 业务知识笔记 — 源自 2026-08 DDA（Device Data Aggregator）生产故障排查

## 背景

2026-08-25 22:57 的一次生产部署（prd CD pipeline）中，`codedeploy.sh` 的 secret
注入逻辑只覆盖了 `internal-api` / `access-api` 两个 family，没有覆盖 vendor batch
的 7 个 family，导致 Fitbit / OMRON connect / アークレイ / MeDaCa 等厂商批处理任务
的认证 secrets 变成空值，调用厂商 API 全部返回 401。

止损后厂商各自的数据恢复情况不同：アークレイ、MeDaCa 走**游标机制**，rule 重新
启用后可自动回填；OMRON connect 走序列号机制，完全无数据丢失；而 **Fitbit** 没有
游标机制，只能拿"当天 + 前一天"数据，故障期间的缺口不会自动补齐，需要单独写代码
回填（影响约 601 名患者，预估执行耗时约 2 小时）。

这篇笔记记录 Fitbit 为什么会做成这样、以及它跟游标机制的本质区别。

## 核心区别一句话

- **游标（Cursor）**：判断依据是"你上次停在哪个具体的点"——记住的、可以是任意久
  以前。
- **Fitbit 滑动窗口**：判断依据是"现在是几号"——只跟当下时间有关，跟你上次停哪
  完全没关系。

书签比喻：游标就像书签精确夹在第 158 页，不管隔了 1 天还是 30 天，一定能接着读；
Fitbit 则完全没有书签，每次来都只给"今天和昨天"，不管你上次是什么时候来的。

### 代码逻辑对比

```text
# Fitbit 现在的写法（写死）
start_date = 今天 - 1天    # 永远是"昨天"
end_date   = 今天          # 永远是"今天"

# 如果 Fitbit 有游标（假设）
start_date = last_get      # 上次成功同步到的时间点（变量）
end_date   = 今天
```

`last_get` 是几天前不重要，只要 API 支持按任意区间查询，中断多久都能把缺口一次性
追齐——这跟 SQL 里 `WHERE updated_at > :last_get` 是一个道理。

Welby 这次的问题不是 Fitbit 官方 API 做不到区间查询，而是 `fitbit_usecase.go`
这段对接代码历史上就没实现"记住 last_get、拿它当起始时间去查"这套逻辑，而是简单
写死成"每次固定问最近 2 天"，没考虑过中断超过 2 天的边界情况。这也是为什么这次
故障后需要单独写 backfill 脚本手动补数据，而不能靠重新 enable rule 自动解决。

## 为什么 Fitbit 选择滑动窗口而不是游标：四个架构取舍

### 1. 数据特性：不可变日志 vs 允许延迟与回溯修正

- 游标适用于只增不改（append-only）的流水数据（消息队列、日志、交易流水）——一旦
  生成绝对不会变，游标只需一路向前推进。
- Fitbit 数据有**延迟落盘**（手环离线几天才连手机蓝牙上传）和**云端算法二次纠偏**
  （夜间重新计算昨天的睡眠阶段/心率曲线）的特点。如果用传统自增游标，一旦游标
  越过了昨天，昨天被云端修正的数据就再也同步不到；而滑动窗口每次都重新拉取过去
  2~3 天的数据，刚好顺便把历史修正的数据一并覆盖刷新。

### 2. 状态管理责任：有状态 vs 无状态

- 游标机制**有状态（stateful）**：必须在高可用数据库里精确持久化保存每个用户的
  `last_processed_pointer`。这个保存点一旦因缓存失效、数据库故障或逻辑 bug 损坏
  丢失，整个同步链路就会死锁或重复拉取。
- Fitbit 机制**无状态（stateless）**：API 不需要知道"你上次查到哪"，请求参数完全
  由当前系统时间决定。逻辑简单，接口天生幂等，系统崩了重启直接拿当下时间算区间
  即可，不存在"保存点丢失"的问题。

### 3. 服务器负载防护：边界查询防暴击

- 游标机制的隐患：某个大型第三方应用断连半个月，修复后用旧游标发起请求，会触发
  巨大的历史数据回溯，可能瞬间从数据库拉出几百万条数据，把 API 服务器打瘫。
- Fitbit 的自我保护：滑动窗口相当于在 API 层强制加了数据上限。不管客户端断连 3
  天还是 3 年，单次请求返回量永远被限制在 2 天以内，计算资源消耗恒定且可预测。

### 4. 底层存储与索引架构

- 游标依赖全局单调递增索引（如 `WHERE auto_id > cursor` / `WHERE updated_at >
  cursor`），需要数据库维持昂贵的全局增量索引。
- Fitbit 体量极大，更适合按日期/时间分片（time-series partitioning）存储——按
  `YYYY-MM-DD` 分块调取极快，但在全量时序数据上跑"跨日期的增量游标"查询开销很高。

## 对比表

| 维度 | 游标机制（Cursor） | Fitbit 滑动窗口机制 |
|---|---|---|
| 设计哲学 | 精确追踪、不漏一条 | 保证最新、无状态、边界可控 |
| 状态维护 | 有状态：必须持久化存储保存点（offset） | 无状态：仅依赖当前系统时间计算 |
| 对历史修改的处理 | 很难捕捉过去数据的重新计算/修正 | 自动覆盖并刷新过去 2 天内的修正数据 |
| 故障恢复能力 | 自动补全中断期间的所有数据 | 超过窗口期的历史数据自动、彻底丢失 |
| 服务端压力 | 恢复连接时易引发大流量冲击（backfill） | 流量与计算量恒定，天然防暴击 |

## 结论

Fitbit 的滑动窗口不是"能力缺陷"，而是在**数据会被事后修正**、**无状态简单可靠**、
**服务器防暴击**、**时序分片存储效率**这四个维度上的合理取舍。代价是：一旦对接方
（Welby 这边）中断同步超过窗口期（2 天），缺口不会自动补齐，必须靠额外的 backfill
逻辑手动追回——这正是本次故障里 Fitbit 单独占用最多修复精力的原因。

## 补充问答：常见误区与背景知识

### "没实现" vs "没考虑边界情况"，哪个更准确？

不是"完全没实现" Fitbit 的对接逻辑——Fitbit 的厂商 API 对接框架跟タニタ、OMRON
connect 是同一套，能正常调用、能正常拉数据。区别只在于"往前查多久"这一行逻辑：

```go
// アークレイ / MeDaCa（游标式）
startDate := lastGetCursor  // 变量，记住上次到哪
endDate := now

// Fitbit（固定窗口）
startDate := now - 2days    // 写死，永远是"今天往前推2天"
endDate := now
```

更准确的说法是：**这是一直存在的架构限制（技术债），这次故障第一次把它暴露出来**，
而不是"这次部署产生的新 bug"。平时 batch 任务几十分钟就同步一次，2 天缓冲永远够用，
所以这条边界从没被真正撞到过；这次因为 secrets 缺失中断了近 3 天，超出固定窗口，
缺口才第一次显现。团队后续走的是单独开 backlog 工单做一次性人工 backfill，而不是
"紧急重写"，也印证了这在内部视角里更像"已知限制"而非"紧急 bug"。

> 需要澄清：Fitbit 官方 API 本身是否支持"给我某个历史时间点之后的所有数据"这种
> 区间查询，这段故障记录里没有直接验证过，只是行业惯例的推测。真正被确认存在
> 限制的，是 Welby 自己 `fitbit_usecase.go` 里写死的固定窗口逻辑。

### secrets 是什么，为什么会"丢"

secrets 指系统调用厂商 API（Fitbit、OMRON 等）时用来证明身份的认证凭证（API Key /
Client Secret / Access Token 一类）。可以类比门禁卡：

- Welby 系统去敲 Fitbit 的门，要数据；
- Fitbit 服务器要求先亮门禁卡（secret）验证身份；
- 没带卡（secrets 为空）就直接拒绝，返回 `401 Unauthorized`。

这次不是"卡片丢失"，而是**部署时压根没被塞进去**：

1. secrets 平时存放在 AWS Secrets Manager / SSM Parameter Store 这类密钥保管箱里；
2. 部署脚本 `codedeploy.sh` 负责在每次部署时把密钥从保管箱取出来，注入进要启动的
   程序；
3. 2026-08-25 22:57 那次部署，脚本里"该往哪些程序塞密钥"的清单只写了
   `internal-api`、`access-api` 两类，漏掉了 vendor batch 的 7 个 family；
4. 这几个 vendor batch 程序启动后密钥格子是空的，一调用厂商 API 就被拒绝。

所以准确说法是"该发的东西没发到位"（部署脚本配置遗漏），而不是"发出去之后弄丢了"。
根治方案 PR #105 就是把 `codedeploy.sh` 里这份"该塞密钥的清单"补全。

### `.sh` 文件是什么

`.sh` 是 Shell Script（脚本文件）——把一系列 Linux 命令按顺序打包写在一个文件里，
执行这一个文件就等于自动按顺序敲完所有命令。例如 `codedeploy.sh` 大致逻辑（示意）：

```bash
#!/bin/bash
echo "开始部署..."
aws secretsmanager get-secret-value --secret-id fitbit-api-key   # 从保管箱取密钥
cp config.json /app/                                              # 塞进程序目录
systemctl restart internal-api                                    # 重启服务
```

在部署流水线（CD pipeline）里，`.sh` 脚本通常负责"拉代码、放配置、注入密钥、
重启服务"这类操作。可以理解为：`.sh` 文件是自动化操作清单，跟写一个函数逻辑类似，
只是操作对象是服务器系统层面的东西（文件、进程、密钥），而不是网页界面。这次故障
的根因就藏在这份清单"该给哪些程序注入 secrets"的部分写漏了。

### タニタ（Tanita）是什么

日本知名健康测量器材厂商，主打体重计/体组成计（测体脂率、肌肉量）、血压计、计步器
等产品。在这次故障里是 Welby 对接的厂商之一：用户用タニタ体重秤测量后数据同步到
タニタ云端，再由 Welby 的 DDA 系统拉取过来，存入用户的健康档案（マイカルテ）。

## 行业视角：三种同步机制的普及程度排名

Fitbit 的滑动窗口在整个软件工程 / API 设计领域里属于**特例**，不是主流。按行业
使用广泛程度排序：

### 1. 最普遍：序列号 / 游标机制（Sequence / Cursor）——行业标准答案

只要涉及"数据同步"、"分页"或"事件流"，绝大多数企业首选此方案。

- **典型应用**：Stripe、GitHub、Twitter(X)、Slack、Meta 等一线 API 的
  `starting_after` / `cursor` 分页（例：`GET /v1/charges?starting_after=ch_12345`）；
  Kafka、Pulsar 的 Offset 消费位点；MySQL Binlog / Debezium 等 CDC 增量捕获。
- **为什么最普及**：性能极高（游标查询直接命中索引，远优于 `OFFSET 10000` 翻页）；
  精准可靠，完美解决断点续传，既不重复也不漏。

### 2. 次普遍：时间戳 + ID 复合游标（Timestamp Cursor）——通用业务的低成本方案

企业内部系统、中小型项目里非常常见，例如 CRM/ERP 数据导出、业务库间的日常增量
同步：`WHERE updated_at >= '2026-08-28 00:00:00' AND id > 100`。之所以常用，是因为
关系型数据库表天生自带 `created_at`/`updated_at`/主键 `id`，不需要专门设计序列号
系统就能直接搭出一个游标，零额外成本。

### 3. 相对少用：无状态滑动窗口（Sliding Window）——特定领域的特殊取舍

在通用 Web 开发中很少见，因为它的"健忘"特性对第三方开发者不友好——断连稍久就丢
数据。典型应用集中在：IoT / 健康穿戴设备同步（Fitbit、Garmin）；日切统计报表 API
（只提供"今天/昨天"汇总）；故意限流防暴击的公开免费 API。

属于特例的原因，本质是**业务逻辑倒逼架构**：手环数据容易离线延时上传，云端还会
事后用算法修正历史睡眠/心率；如果强行用游标，历史修正的数据就再也传不出去。厂商
宁可牺牲"故障后的历史数据补全能力"，也要把单次请求的资源消耗死死限制住，防止有人
写坏代码不断发起历史全量重拉。

**总结**：标准后端开发优先选序列号/游标机制；只有数据会事后修正、设备经常离线、
且要求 API 彻底无状态防暴击这类特殊场景，才会采用 Fitbit 式滑动窗口。

## 为什么"强行用游标"会丢数据或产生脏数据

游标机制的铁律是**"永远只看未来，不回头看历史"**——查询条件永远是
`WHERE timestamp > 游标点` 或 `WHERE sequence_id > 游标点`。一旦遇到离线延时上传
或云端事后修正，数据落下的位置恰恰在游标点的**后方（历史时间）**，游标从物理逻辑
上就彻底扫描不到它们了。

### 场景一：离线延时上传（"向历史插数据"）

你 8/1～8/3 去山里徒步，手机完全没网，手环把这 3 天数据存进本地芯片。

1. **8/2（第三方发起同步）**：问 Fitbit"给我最新数据"，因为你没网啥也没拿到，但
   游标仍记录下当前处理时间：`游标 = 8/2`。
2. **8/4（手环连网）**：把 8/1～8/3 的数据一口气上传到云端——这批数据的**生理发生
   时间**是 8/1～8/3。
3. **8/5（第三方再次同步）**：带着游标问"给我 `时间 > 8/2` 的所有数据"。结果：
   8/1、8/2 补传的数据因为时间戳 ≤ 8/2，直接被过滤掉，永远漏掉。

### 场景二：云端事后算法修正（"修改历史数据"）

睡眠/心率得分不是实时死板算出来的，云端 AI 会在夜间做二次修正。

1. **8/1 晚上**：手环初判你睡了 6 小时，第三方同步记下"8/1 睡眠 6 小时"，游标
   推进到 8/1。
2. **8/2 下午**：云端跑完夜间深度学习模型，结合全天 HRV 重新计算：你其实睡了 8
   小时（2 小时深睡被误判成清醒）。数据库把 **8/1** 的记录改成 8 小时。
3. **8/3（第三方同步）**：带游标问"给我 `时间 > 8/1` 的数据"，直接从 8/2 开始找。
   被改成 8 小时的那条记录因为日期属于 8/1（过去），永远不会再被吐出来——第三方
   数据库里永久留存错误的"6 小时"。

### 追问：为什么不能用 `updated_at`（更新时间）做游标？

技术上加一个 `updated_at` 字段、查询改成 `WHERE updated_at > 游标`，确实能在修改
历史数据时把旧记录捞出来。但 Fitbit 依然不采用，原因有二：

1. **第三方处理成本极高**：收到"3 天前某条睡眠记录被修改"的通知后，第三方要写
   复杂逻辑去定位并覆写那条历史记录、重算 3 天前的所有报表——绝大多数第三方开发者
   根本写不好这套逻辑。
2. **海量时序数据的数据库灾难**：手环每 5 秒上传一次心率，一人一天近两万条数据。
   一旦云端修正昨天的算法，导致昨天几万条数据的 `updated_at` 全部刷新，这个游标
   会在下次拉取时引发瞬间的数据暴击。

### 滑动窗口如何优雅解决

Fitbit 的无状态滑动窗口（每次直接拿"今天 + 前一天"全量数据）用极简方式搞定了
上面两个难题：无论是延时补传昨天的步数，还是云端修正了昨天的睡眠，第三方明天调用
API 时拿到的都是**昨日全量快照**——不需要做复杂的增量比对，直接**整块覆盖
（Overwrite）** 本地数据库即可。这种"以直接覆盖代替增量追踪"的设计，用极低的
架构成本天然解决了历史修正与延时补传问题。

### 比喻：老师改试卷分数

容易混淆的核心点是：**"数据修改发生的时间"（8/2）** 和 **"数据本身的归属日期"
（8/1）** 是两回事。

- **8/1（考试日）**：你参加"8/1 的考试"，试卷顶部写着考试日期 8/1，老师批出 60
  分。记账员抄走试卷，账本盖章"8/1 的试卷已处理（游标 = 8/1）"。
- **8/2 下午（老师改分）**：老师发现判错，把这张"8/1 的试卷"分数改成 80 分——注意
  试卷顶部的日期依然是 8/1，不会变成 8/2。
- **8/3（记账员再来拉数据）**：翻开账本，问老师"请把考试日期在 8/1 之后
  （`试卷日期 > 8/1`）的新试卷给我"。老师手里两张卷子：改成 80 分的那张日期仍是
  8/1——记账员说"这张我处理过了，不要"（改分失效！）；另一张 8/2 新考的日期是
  8/2——记账员说"符合 `> 8/1`，拿走"。

还原到代码层面：

```sql
SELECT * FROM sleep_table WHERE sleep_date > '2026-08-01';
```

那条被修改的睡眠记录，`sleep_date` 永远是 `2026-08-01`（那是你睡觉的生理日期）。
8/3 带着游标查询 `sleep_date > '2026-08-01'`，数据库一看这条记录的 `sleep_date`
并不大于 `2026-08-01`，直接排除。结果：8/2 云端虽然重新计算了，但因为数据本身的
"时间标签"还是 8/1，基于时间标签推进的游标永远把它当成"已处理过的旧数据"，再也
不会去碰它。**这不是代码 bug，而是为了降低成本、保证系统稳定而故意为之的架构设计
取舍（Design Trade-off）。**

## 如果要"修复"Fitbit，让它像 OMRON 一样支持无限追溯，代价有多大

1. **数据库性能与算力成本爆炸**：血压计一天只产生 1~2 条记录，而 Fitbit 手环每 5
   秒记录一次心率，一人一天近 2 万条数据，全球几千万用户每天产生数千亿条时序数据。
   为支持按 `updated_at` 查询历史任意时刻的修改，数据库必须为千亿级数据建立全局
   复杂索引，存储与 CPU 算力成本翻倍增长。
2. **无法承受的"雪崩效应"（流量风暴）**：一旦发生大型故障或断网半个月，恢复连接
   那一刻几百万用户的 App 会同时请求"把过去 15 天数据全部补给我"，瞬间把 API
   服务器吞吐量放大十几倍，足以把数据中心和带宽拉爆，造成第二次更大规模瘫痪。
3. **破坏整个第三方生态**：全球成千上万开发者（医院、保险公司、健康 App）已基于
   现有 API 写好"每天拿最近 2 天数据直接覆盖"的代码。若 Fitbit 突然改成"按序列号
   吐出增量变更"，会导致全球对接方系统集体崩溃，需要所有开发者重写适配。
4. **商业 ROI 不划算**：Fitbit 定位是面向 C 端的运动手环，不是医疗级监护设备。
   普通用户即使一年因故障漏掉 2 天步数也毫无影响；为了这 0.01% 的极端场景去维护
   一套成本极高的分布式游标系统，在商业上并不划算。

类比：这就像"为什么轻便共享单车不装车厢"——不是造不出车厢，而是一旦装了，车就会
变得笨重、昂贵且易损坏。Fitbit 选择了"轻便简单但偶尔会漏"的架构，放弃了"昂贵复杂
但绝对不漏"的架构。
