# DDA 到底是什么：多厂商数据 → 统一 FHIR 出口

> 业务知识笔记 — 源自 2026-08 TISI 外部审计 e9 项目调查（機器連携取得情報一覧）+
> 2026-08 DDA 生产故障排查
> 姊妹篇：[fitbit-cursor-vs-sliding-window.md](./fitbit-cursor-vs-sliding-window.md)
> 讲厂商同步机制细节；[dda-incident-secrets-and-rule-ops.md](./dda-incident-secrets-and-rule-ops.md)
> 讲故障运维；[er-diagram-and-fhir-resource-mapping.md](./er-diagram-and-fhir-resource-mapping.md)
> 讲 FHIR 资源本身是什么。这篇讲 DDA 这个系统整体是干什么用的。

## 一句话结论

**"DDA 是个过滤器，各家厂商数据拿到手，出口是 FHIR 数据"——方向完全对，但
"过滤器"这个词稍微用轻了。** 更准确的说法是**适配器/转换器（Adapter）**：

- "过滤"暗示的动作是"筛选、去掉一部分、留下一部分"；
- DDA 真正做的事是**格式翻译**——七八家厂商各自的数据格式、认证方式完全不同，
  DDA 的核心职责是把这些五花八门的输入，统一"翻译"成一种标准形状（FHIR）之后
  再往下游送，而不是简单地"挑一挑、滤一滤"。

```
Fitbit（OAuth token + 滑动窗口）──┐
OMRON connect（序列号机制）───────┤
タニタ（序列号机制）─────────────┤
アークレイ e-SMBG（游标机制）────┼──▶  DDA（认证 + 拉取 + 格式转换）  ──▶  FHIR Observation
Abbott フリースタイルリブレ ──────┤                                        （+ 内部 lifelogs 表）
A&D（已下线，见下文）────────────┤
MeDaCa ───────────────────────────┘
```

## 业务层面：DDA連携到底是什么（完全零基础版）

先不讲代码，讲清楚"連携"这件事在业务场景里到底发生了什么：

**背景：病人自己家里有健康监测设备**

比如一个 CKD（慢性肾病）/高血压病人，家里放着欧姆龙的血压计、Fitbit 手环
（测心率、步数）、タニタ的体脂秤、雅培 Libre 血糖仪（贴在皮肤上的连续血糖
监测贴片）。这些设备**不是 Welby 造的**，是各厂商自己的产品。设备测出来的
数据，**首先存在厂商自己的服务器/App 里**——比如用欧姆龙血压计测完血压，
数据先同步到欧姆龙自己的 App（OMRON connect）里，不是直接跑到 Welby 的
マイカルテ里。

**"連携"（れんけい）= 对接/打通**

病人在マイカルテ里操作一下"授权"，相当于说"我同意让 Welby 去欧姆龙那边把
我的数据拉过来"。之后 Welby 系统会**定期调用欧姆龙的 API**，把这个病人的
血压数据"拉"过来，放进 Welby 自己的系统，最终显示在マイカルテ的健康记录
里。这个"打通两边、把数据从厂商那边搬过来"的动作，就叫"連携"（integration/
linkage）。

**DDA = 干这件"搬数据"活儿的模块**——对应下面"一句话结论"里说的
Adapter/转换器角色。

**一句话总结整个链路**：

病人的设备（欧姆龙/Fitbit/雅培等）→ 厂商自己的云端 → **DDA 连携**（Welby
定期去拉数据）→ Welby 数据库（物理表）→ 转换成 **FHIR Observation** →
显示在マイカルテ给病人/医生看。

"DDA連携"这个词，指的就是"跟某个具体厂商之间，数据打通、能自动同步"这件
事本身——TISI e9（機器連携取得情報一覧）问的就是"我们跟哪些厂商做了这种
连携、每家连携实际取数据取得对不对"。

## 输入端：每家厂商都不一样，这正是 DDA 存在的理由

如果所有厂商给的数据格式、认证方式都长得一样，根本不需要 DDA 这一层——每家
厂商直接怼一个标准接口进来就行。现实是每家都不一样：

| 厂商 | 认证 | 同步机制 |
|---|---|---|
| Fitbit | 用户级 OAuth token（会过期，见下文） | 无状态滑动窗口（今天+昨天，见 [fitbit-cursor-vs-sliding-window.md](./fitbit-cursor-vs-sliding-window.md)） |
| OMRON connect / タニタ | app 级 API Key | 序列号机制 |
| アークレイ（e-SMBG）/ MeDaCa | app 级 API Key | 游标（cursor）机制 |
| A&D | app 级 API Key（提供方已下线，见下文） | 曾经存在，2025-09-09 从前端移除 |

DDA 要为每一家单独写一套"怎么认证、怎么分页、断连了怎么补数据"的适配逻辑——
这就是为什么 2026-08 那次故障里，同样是"secrets 变空"，タニタ/アークレイ/
MeDaCa 靠 rule 重新 enable 就能自动补数据，Fitbit 却需要单独写 backfill 脚本
（同一个故障原因，各厂商适配层的容错能力完全不同）。

## 输出端：FHIR 只是其中一半，还有一份内部 lifelogs

从故障回填的 DRYRUN 描述能看出 DDA 的写入路径其实有两段：

> DRYRUN 只做"拉取 + 解析"，跳过"**写 lifelogs / 写 FHIR**"这一步

也就是说厂商数据被 DDA 转换后，会**同时**写进两个地方：

1. **FHIR Observation 资源**——标准化的医疗数据格式，跟其他系统（マイカルテ
   前端、welby_base 主库）用统一语义对接，见 [er-diagram-and-fhir-resource-mapping.md](./er-diagram-and-fhir-resource-mapping.md)
   里"FHIR 资源逻辑映射"的部分。
2. **lifelogs（内部生活日志表）**——更贴近厂商原始颗粒度的记录（比如心率、
   步数这类高频数据），供内部展示/统计用，不一定每条都需要走 FHIR 语义分类。

所以"出口是 FHIR 数据"这句话对了一半：FHIR 是主要出口、也是外部审计/跨系统
对接关心的那部分，但严格说 DDA 是**双路输出**，不是单一管道。

## 一个容易踩的坑：不是所有"机器连携画面"上的东西都是 DDA

这是这次 e9 调查里发现的、跟直觉不符的一点：UI 上的"機器連携一覧"画面会把
Fitbit/OMRON 这些真设备，跟がまっと！（がまごおりデジタル健康プラットフォーム，
蒲郡市市民健康平台）、都農町、会津若松+ 这类**市政平台账号绑定**功能摆在同一
个页面里，看起来像是同一类东西，但底层走的是两套完全不同的系统：

- **真设备厂商**（Fitbit/OMRON/タニタ/アークレイ/Abbott/A&D/MeDaCa）
  → 走 **DDA_DOMAIN**，需要 DDA 认证+拉取+转换这一整套逻辑，本文讲的是这一半。
- **市政平台账号绑定**（がまっと！/都農/会津若松+）
  → 走 **FHIR_DOMAIN 代理**，本质是"扫 QR 码把マイカルテ账号跟市政平台账号
  关联"，DDA 只是原样透传请求，不做任何厂商数据拉取或格式转换。

结论：**判断"这是不是 DDA"不能看它出不出现在"机器连携"画面上，要看它是否
真的经过"认证 → 拉取厂商原始数据 → 格式转换成 FHIR/lifelogs"这一整套流程。**
がまっと！长得像设备连携，其实只是个账号绑定入口，跟 DDA 的核心职责（多厂商
数据适配）没有关系。

## 追问：がまっと！扫码绑定为什么不用走 DDA

关键不在"扫码"这个动作本身，而在于**扫码之后有没有"厂商原始数据"需要持续
拉取转换**。

- **DDA 存在的意义**：厂商设备会持续产生测量数据（心率、体重、血糖……），
  存在厂商自己的云端。DDA 的活儿是**反复发生、持续同步**——今天问一次，
  明天再问一次，永远在问"有没有新数据"，拿到后转换成 FHIR/lifelogs。
- **扫码绑定是完全不同的事**：がまっと！的 DDA 侧只实现了两个接口——生成
  QR 码、查询绑定状态（见 `gamatto_api_design.md`：只有 `/gamatto/qr` 和
  `/gamatto/patient/connected`，没有任何"拉取健康测量数据"的接口）。扫码
  绑定做的事情是：**患者扫一下码，把"マイカルテ账号 ID"跟"がまっと平台
  账号 ID"关联起来**，写进一张关联表（`external_service_patient_link`/
  `patient_tsuno_link`）——这是**一次性**的身份关联动作，做完就结束，没有
  后续"每隔 15 分钟去问一次がまっと有没有新数据"这种持续同步。

逻辑链：没有厂商原始测量数据 → 就没有"格式不同、需要翻译"这个问题 → 就不
需要 DDA 那套"认证 + 批处理拉取 + 格式转换"的机器。唯一要做的只是"记一下
这两个 ID 是同一个人"，这个简单关联动作直接找 FHIR_DOMAIN（本来就管着
patient 身份关联的地方）就能办，犯不着走 DDA 这套为"持续同步厂商数据"设计
的重型管道。**DDA 是为"有持续数据流"这件事设计的，扫码绑定只是"认个身份"，
压根没有数据流要处理，所以自然用不上 DDA。**

## 追问："DDA 不就是轮询吗"——轮询只是外层调度壳，不是全部

"轮询"说对了一半：**触发机制确实是轮询**，不是被动接收厂商推送（webhook）。
故障记录里"约每 15 分钟一次"、"rule ENABLED/DISABLED"控制的就是这个轮询
节奏的开关。

但"轮询"只回答了"**多久问一次**"这一个问题，DDA 真正的复杂度在另外两块，
光说轮询会漏掉：

1. **问的时候带什么参数，每家还不一样**——同样是"轮询"，OMRON/タニタ用
   序列号（"给我序列号 > X 的"），アークレイ/MeDaCa 用游标（"给我时间
   > lastGet 的"），Fitbit 用写死的滑动窗口（"给我今天和昨天的"，不管
   上次问到哪）。同一个"轮询"外壳下，每家厂商的查询策略本质完全不同，这也
   是为什么故障恢复时タニタ/アークレイ/MeDaCa 能自动补数据、Fitbit 不能
   （详见 [fitbit-cursor-vs-sliding-window.md](./fitbit-cursor-vs-sliding-window.md)）。
2. **问回来之后要做格式转换**——轮询只是"拿到一坨厂商原始格式的数据"，DDA
   还要把这坨数据解析、转换成 FHIR Observation + lifelogs 两种标准格式再往
   下游写。这一步跟"多久问一次"没关系，是纯粹的"翻译"工作。

一句话：**轮询回答的是"什么时候问"，DDA 的核心复杂度其实在"问什么"（每家
参数不同）和"问回来怎么处理"（格式转换）这两块——轮询只是外层的调度壳，
不是 DDA 的全部工作。**

## 追问：Libre 是什么、测得准不准、多少钱

**Libre（正式名 Abbott フリースタイルリブレ）是雅培出的连续血糖监测（CGM）
设备**——一枚贴在上臂皮下的小型传感器，每隔几分钟自动测一次血糖，不用像
传统血糖仪那样扎手指采血，数据通过手机 App/读取器同步到厂商云端。DDA 对接
的正是这条"厂商云端 API"通路，把用户授权后的血糖读数拉进 Welby 系统（见
`.env.example` 里的 `LIBRE_DOMAIN`、`LIBRE_AUTH_DOMAIN`、`LIBRE_CLIENT_ID`
等对接凭证）。

**准确度和扎手指采血是不是一样——不完全一样，但足够接近临床可用**：

- Libre 测的是**组织间液**里的葡萄糖浓度，不是直接测血液——血糖变化传导到
  组织间液需要几分钟生理延迟，所以数值曲线会比指尖血糖略有滞后，尤其在血糖
  快速升降时更明显。
- 行业通用的准确度指标叫 **MARD（平均绝对相对误差）**，数值越低越准。Libre
  系列公开的临床数据大致在 7%~11% 这个区间，跟传统指尖血糖仪（常见 MARD 也
  在 10% 上下）属于同一量级，不是"明显更不准"，但也不是"完全等同"。
- 厂商自身也建议：如果读数和身体感觉对不上（比如怀疑低血糖但数值不低），或
  者血糖快速变化时，仍建议扎手指验证——不能 100% 替代传统采血检测。

**多少钱——这块没有把握给出准确数字，不写死金额**：传感器一般 2 周一换、需
要持续购买，价格因国家、是否有医保覆盖差别很大（日本对符合条件的糖尿病患者
——尤其是胰岛素治疗患者——有健保覆盖，自费价格因渠道/时间浮动）。如果业务
上需要日本当前的精确价格，建议直接查雅培日本官网或药局最新报价，这里给的只
是"大致数量级+定价逻辑"，不代表当前准确金额。

## 追问：DDA 是不是相当于 MVC 里的 View，FHIR 相当于 Controller

不是，这个类比对不上——MVC 是**面向 UI 界面**的架构模式（View=给用户看的
画面，Controller=处理用户操作、协调 Model 和 View），而 DDA 和 FHIR 都是
纯后端、跟"界面展示"完全无关的概念，硬套会两头都对不上：

- **DDA 不是 View**——DDA 做的是"去各厂商那边采集数据"这件纯后端工作，用户
  根本看不见这个过程，跟"展示"毫无关系。
- **FHIR 也不是 Controller**——FHIR 只是"数据该长什么格式"的标准/规范，更
  接近 MVC 里的 **Model**（数据表示）这个角色，不负责"处理用户操作"。

如果一定要在软件架构里找对应角色：**DDA ≈ 数据采集适配层（Adapter），
FHIR ≈ 标准数据模型（Model/Schema）**。这两者都发生在用户看不到的后台管道
里，跟 MVC 关心的"界面怎么呈现、怎么响应操作"是完全不同层面的问题。

## 追问：マイカルテ 和 サイログ 为什么各自独立设计 FHIR mapping——サイログ 到底是什么

这是 e4 调查里冒出来的一个问题：Slack 上说"Welby各サービス(マイカルテ、サイログ等)
はFHIRマッピングをそれぞれ独自に設計しており"，但**没有任何文档明确说过
"サイログ 是什么"**——这条信息完全是靠 grep 代码库才拼出来的（先在各仓库
README/markdown 里搜"サイログ"，一无所获；再在整个
`welby-fhir-server-aggregator-platform` 仓库全文搜索，排除掉"抗サイログ
ロブリン抗体"——甲状腺球蛋白抗体，一个医学检验指标名，纯属字符串碰巧撞上
——之后，才在 `migration/master/0014_thylog_questionnaire.sql` 这个 **SQL
迁移文件**里找到真正线索）。

**サイログ（读作 Thylog，Thyroid + Log）是 Welby 跟制药公司 Amgen（安进）
合作做的一款甲状腺疾病患者管理 App**，跟マイカルテ是完全不同的两个产品：

- Questionnaire（FHIR 问卷）publisher 写的是 `AmgenThylog Publisher`
- API 域名是 `amgen-thyroid-api.welby.jp`
- 问卷内容全是甲状腺相关：现在治疗中的甲状腺疾病、有没有做过甲状腺摘除
  手术、有没有服用抗甲状腺药、甲状腺眼症、QOL 生活质量评估等

**这就完全解释了为什么两边会各自独立设计 FHIR mapping**：マイカルテ 是
WPDP 平台的通用医疗记录产品，サイログ 是给 Amgen 甲状腺患者项目单独做的
垂直病种管理 App，业务场景、底层数据结构完全不同（甲状腺患者日常问卷 vs
マイカルテ 的通用病历/检验数据），物理表设计不可能相同，FHIR mapping 自然
也各自独立——不是团队没协调好，是两个产品本来就服务于不同的业务目的。

## 厂商背景小知识（跟"设备连携"列表里几个名字相关，方便认脸）

- **Fitbit**：2021年1月14日被 Google 正式完成收购（21亿美元），但协议其实
  2019年10月31日就签了、11月1日就公布，因为要过欧盟等地反垄断审查，拖了一年
  多才交割完成。
- **がまっと！**：名字来自**蒲郡市**（Gamagōri，爱知县一个城市）的数字健康
  平台——"がま"取自"蒲郡(Gama-gōri)"的读音，加上"っと"这个日语里常见的、
  带点可爱亲切感的后缀（类似地方吉祥物/市民计划常用的命名套路），拼成
  "がまっと"，本质就是"地名+卖萌后缀"，不是什么复杂缩写。
- **欧姆龙（OMRON）**：欧姆龙自己不生产、不卖鼠标这个产品，但它是全球最大
  的"鼠标微动开关（click 开关）"供应商——罗技、雷蛇等品牌鼠标里那颗负责
  "咔哒"点击手感的零件很多用的就是欧姆龙的（游戏鼠标常标榜的"2000万次点击
  寿命 Omron 开关"说的就是这个）。这个细分市场欧姆龙份额约 50%。欧姆龙真正
  的主营业务是精密电子元件（传感器、PLC 工业自动化）和**家用血压计/体重体
  脂秤等健康设备**（全球家用血压计市场份额第一）——后者才是它出现在这次
  "设备连携"厂商列表里的真正原因。

## 为什么这套"多进一出"的设计对 TISI 审计/e9 调查很重要

外部审计方关心的"機器連携取得情報一覧"文档，本质就是要一份**准确的"输入端
清单"**——现在到底接了哪几家厂商。这份清单会过时，正是因为 DDA 的输入端
（厂商列表）会随业务变化而增减（A&D 2025-09 下线、MeDaCa 2025-12 上线），
但输出端（FHIR/lifelogs 的格式）相对稳定，不会跟着每次厂商增减而变——所以
外部视角容易忽略"这份清单该更新了"，因为系统整体"看起来"照常运作，没有明显
故障信号。
